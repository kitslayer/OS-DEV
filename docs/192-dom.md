# Milestone 192 — a minimal DOM (interactive browser)

The browser is now **interactive**: page JavaScript can find an element by id and
read or change its content, and the page updates in place. This is the long-
deferred north star — the browser was already fetching and rendering the real
HTTPS web; now scripts can manipulate what's on screen.

```html
<p>Counter: <b id="count">0</b></p>
<p>Message: <span id="msg">…</span></p>
<a href="javascript:
   var c = parseInt(document.getElementById('count').textContent) + 1;
   document.getElementById('count').textContent = '' + c">increment</a>
<a href="javascript:document.getElementById('msg').textContent = 'Hello from a real DOM!'">set</a>
<a href="javascript:document.getElementById('msg').innerHTML = 'now <b>bold</b>'">set HTML</a>
```

Clicking a link runs the JS, mutates the named element, and the page re-renders
showing the change — **verified in the real kernel** (`DOM.HTM`: the counter goes
`0 → 1`, and "Message" changes to "Hello from a real DOM!").

## API

- `document.getElementById(id)` → a **live element handle**.
- `element.textContent` / `element.innerText` — read or assign the element's text.
- `element.innerHTML` — read or assign raw inner HTML.
- `element.id` — the id.

Assigning to `textContent`/`innerHTML` mutates the page and re-renders.

## How it works (across `js.c` and `browser.c`)

The renderer is a flat **token stream**, not a DOM tree — so rather than build a
tree, the DOM operates on the **page source** (`b->raw`) and re-renders, reusing
the same model as `document.write` / `localStorage`:

- **`js.c`:** `getElementById` returns a `V_ELEMENT` object (a new obj kind; the
  id is stored in `vals[0]`). `eval_member_get` and member-assignment intercept
  `V_ELEMENT` and call host **DOM callbacks** (`js_set_dom(get, set)`), exactly
  like the existing storage/`document.write` callbacks. `V_ELEMENT` is covered by
  the M191 `obj_keyed` gate, so introspecting one (`JSON.stringify`, `Object.keys`)
  is safe.
- **`browser.c`:** `dom_find` locates `<tag … id="ID" …>INNER</tag>` in the body
  region of `b->raw` (backing up to the opening `<`, reading the tag name, and
  matching the closing tag with a nesting depth count). `browser_dom_get` copies
  `INNER`; `browser_dom_set` splices the new content in (a bounds-checked
  `memmove` of the tail when the length changes — so longer/shorter replacements
  work) and calls `parse_html` to re-render in place.

## Limitations (next steps)

- `textContent` is inserted/returned as raw (not HTML-escaped) — fine for plain
  text; an element's existing child markup is included in a read.
- Re-rendering resets the link selection, so repeated clicks need a re-`Tab`
  (preserving the selection across re-render is a follow-up).
- No `querySelector`, element creation/removal, `addEventListener`, or attribute
  access yet — `getElementById` + `textContent`/`innerHTML` is the foundation;
  those build on the same source-mutate-and-re-render mechanism.

Covered by the JS regression suite (the new `V_ELEMENT` kind is `obj_keyed`-safe,
`make jstest` ASan/UBSan-clean); kernel builds clean; verified interactive in-OS.
