# Milestone 142 — ECDSA on NIST P-384

**Goal:** the last big algorithm gap for certificate chains. Modern ECDSA chains
sign the CA-to-CA links with **ECDSA over P-384** (and SHA-384), which milestone
141 still reported "unsupported" (example.com's chain was stuck at 1/3). This adds
P-384 so those chains fully verify.

## How — reusing the P-256 machinery

`ecdsa.c`'s point arithmetic is already generic (Jacobian, `a = -3`, all over the
`bignum` field prime in a global `P`), so P-384 needed mostly **parameters**, not
new math:

- Added the P-384 domain constants (`P384_P`/`N`/`B`/`GX`/`GY`, 48-byte).
- Refactored `ecdsa_p256_verify` into a curve-generic `ecdsa_verify(p,n,gx,gy,b,
  fieldlen, …)`; `ecdsa_p256_verify` and new `ecdsa_p384_verify` are wrappers. The
  DER parse is shared (`der_rs`).
- **Fixed a latent bug the refactor exposed:** the scalar-multiply loop iterated a
  hard-coded `255` bits — fine for P-256 but it *truncated* P-384's 384-bit
  scalar. It now scans `bits-1..0` where `bits` = the curve's order size, so
  P-256 (256) and P-384 (384) both work.
- `tls.c`'s `ecdsa_cert_verify` picks the curve by issuer-key length (P-256 = 65,
  P-384 = 97 bytes) and derives the ECDSA `z` correctly (P-384 uses the full
  48-byte SHA-384, or a left-padded shorter digest).

## Verified

- **Host test** (vs OpenSSL-generated signatures): `ecdsa_p384_verify` accepts a
  valid P-384/SHA-384 signature and rejects a tampered signature and a wrong
  digest; P-256 still verifies (refactor is regression-free).
- **Live, example.com**: the 4-cert EC chain (`example.com` P-256 leaf ←
  `Cloudflare ECC CA 3` ← `SSL.com Transit` ← `SSL.com Root`, the upper links
  ECDSA-P384-SHA384) now reports **`chain: 3/3 issuer link(s) verified`** — up
  from 1/3. The from-scratch P-384 ECDSA validates real CA signatures. No panics;
  the heavy P-384 verifies run on the 256 KB worker stack.

## Next

The from-scratch crypto now covers RSA + ECDSA (P-256/P-384) × SHA-256/SHA-384 —
enough for the common real-world chains. Remaining for *enforced* validation: more
roots in the trust store (so non-Let's-Encrypt chains anchor), then gate
acceptance on `CertVerify && full-chain && anchored` and make it fatal.
