# 302–305: CSS — inline `style=`, `<style>` blocks, cascade, and a scope stack

For its whole life the browser rendered structure (headings, lists, tables,
links, images) but ignored *presentation* almost entirely: the only colour came
from the legacy `<font color>` tag. This arc adds a real — if small — **CSS
engine**: per-element `color` / `font-weight` / `font-style`, set by inline
`style="..."` attributes *and* by `<style>` rules with `tag` / `.class` / `#id`
selectors, cascading correctly and nesting to any depth.

It works on the same constraint as the rest of the browser: there is **no DOM
tree and no layout engine** — rendering is a single forward pass over a flat
token stream (`parse_html` → `handle_tag` → tokens → draw). Everything below is
designed to fit that pass.

## The model: a per-element style *scope*

The renderer already carried a `curcolor` (the active text colour, from
`<font>`) and a `*style` enum (`STY_NORMAL` / `STY_BOLD` / `STY_EM` / …). A CSS
rule that says "this element's text is red and bold" therefore doesn't need a
box model — it just needs to set `curcolor` / `*style` while emitting that
element's content, and restore them at the element's close.

That "set on open, restore on close" is a **scope**, and the browser already had
exactly one of these: the inline-`onclick` scope (`oc_*`), which makes an
element's content a clickable link and restores the prior link state at the
element's matching close, depth-counting same-name nesting so
`<div onclick><div>…</div></div>` ends at the right `</div>`. The whole CSS arc
is built by mirroring that proven scope.

### M302–303: the value parsers (bounded, read-only, reused everywhere)

- `parse_style_color(s, n)` — scans an inline style string for the `color:`
  property (requiring a property boundary before `color` so `background-color`
  is skipped) and hands the value to the existing `parse_color` (named or
  `#hex`).
- `style_prop(s, n, prop, plen, &vs, &ve)` — a generic helper: finds a
  lowercase property at a CSS boundary and returns its trimmed value span.
- `parse_style_textstyle(s, n)` — maps `font-weight: bold|bolder|600..900` →
  `STY_BOLD` and `font-style: italic|oblique` → `STY_EM`.

All three are bounded reads over `s[0..n)` with no writes — the kernel has no
stack guard page and this is untrusted page input, so every index is proven in
range (and fuzzed under ASan/UBSan in review). They are deliberately **reused
unchanged** by the `<style>` engine below, rather than reparsed.

### M302–303: applying it (the single scope)

In `handle_tag`, an element whose inline `style=` resolves a colour and/or a
text-style saves the current `curcolor`/`*style`, applies the new ones, and
restores at its matching close. The text-style is restored *only if `*style` is
still the one we set* — mirroring the `oc_*` scope, so a legitimately-changed
nested style isn't clobbered. A wrong/leaked style under malformed HTML is only
ever a wrong colour (the style value is consumed by `switch`/comparison and a
framebuffer colour — **never an array index**), and is reset on the next parse.

## M304: `<style>` blocks — a real stylesheet

`<style>…</style>` content was previously skipped. Now its body is captured
(mirroring the `<script>` capture) and parsed by `capture_css`:

```
selector { decl; decl }  selector { … }
```

- The **selector** is handed to the existing `sel_parse` (the same matcher
  `querySelector` uses): `tag`, `.class`, `#id`, `[attr]`. Anything more complex
  — descendant combinators, comma groups, `@media` — fails `sel_parse` and the
  rule is simply skipped (fail-closed). Capped at `CSS_MAX` rules.
- The **declaration block** is fed straight to `parse_style_color` +
  `parse_style_textstyle` — the very same value parsers as inline `style=`.

At render time, `css_match` cascades the captured rules onto each element using
*exactly* `sel_match_all`'s per-element checks (`tageq` / `class_has` /
`attr_eq` / `has_attr`), later rules winning per property. Then inline `style=`
overrides per property (proper cascade: author stylesheet < inline). The result
feeds the same scope machinery.

## M305: the scope *stack* — nesting that composes

M302–304 used a *single* active scope: while one was open, a nested styled
element couldn't open its own. That was fine for inline-only pages but crippling
with `<style>` rules — a single `p { color: #333 }` scopes *every* paragraph, so
any `<span class="hi">` inside any paragraph couldn't be styled.

M305 replaces the single scope with a small **stack** (`sc[SC_MAX]`, `sc_sp`):

- A **styled** element pushes a frame (saving the enclosing colour + style,
  applying its own).
- Its matching close pops the frame and restores.
- Same-tag nesting is depth-counted **per frame**: a styled same-tag open pushes
  a *new* frame; an *unstyled* same-tag open just deepens the top frame — so an
  inner `</span>` can't pop an outer `<span>`'s scope early.
- Stack-full is graceful (skip — never overflows); reset empty each parse.

Per-frame semantics are byte-identical to the reviewed single scope; M305 only
*stacks* them. Now `p { color }` + a nested `<span class="red">` renders the
paragraph grey with a red span restored to grey, inline colours nest, etc.

## What still needs a real engine

`color` / `font-weight` / `font-style` map cleanly onto the existing token
attributes, so they work without a layout engine. The rest of CSS —
`font-size` (the renderer has only 1×/2× scale), `text-align`, the box model,
backgrounds, floats, fl/grid — genuinely needs box layout the flat token stream
doesn't have, and remains out of scope. But selectors, the cascade, and nesting
— the *machinery* of CSS — are now real.
